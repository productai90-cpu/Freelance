# سایت تالار مرمر چطور کار می‌کند — توضیح ساده

این فایل توضیح می‌دهد چه ساختیم و هر تکه چه کاری می‌کند. بدون اصطلاح فنی اضافه.

---

## ۱. سایت از دو چیز ساخته شده، نه یکی

این مهم‌ترین چیزی است که باید بدانید، چون بقیهٔ ماجرا از همین می‌آید.

| | |
|---|---|
| **کد اصلی** | چیزی که ما می‌نویسیم. در پوشهٔ `src/` است. خوانا برای آدم |
| **فایل نهایی** | چیزی که مرورگر اجرا می‌کند. در پوشهٔ `dist/` است. غیرقابل خواندن برای آدم |

بین این دو یک مرحله هست به اسم **build**. مثل آشپزی: مواد اولیه (کد اصلی) با هم پخته می‌شوند و غذا (فایل نهایی) بیرون می‌آید. مرورگر فقط غذا را می‌خورد، مواد اولیه را نمی‌فهمد.

دستور `npm run build` همین کار را می‌کند.

**چرا آپلود دستی قبلی جواب نمی‌داد:** شما مواد اولیه را آپلود می‌کردید. مرورگر بازدیدکننده نمی‌توانست بخوردشان.

---

## ۲. گیت‌هاب: انبار کد + آشپز

گیت‌هاب دو نقش دارد:

**انبار.** هر بار `git push` می‌زنید، نسخهٔ جدید کد آنجا ذخیره می‌شود. تاریخچه می‌ماند، پس اگر چیزی خراب شد می‌شود برگشت.

**آشپز.** فایل `.github/workflows/deploy.yml` یک دستور کار است که به گیت‌هاب می‌گوید: «هر وقت کد جدید آمد، خودت build بگیر و منتشر کن.»

```
شما: git push
        ↓
گیت‌هاب: کد را می‌گیرد
        ↓
        npm ci          ← ابزارها را نصب می‌کند
        npm run build   ← غذا را می‌پزد
        ↓
        منتشر می‌کند → سایت زنده
```

پس شما دیگر هیچ‌وقت build دستی نمی‌گیرید. فقط push می‌کنید.

---

## ۳. مشکلی که Supabase حلش کرد

سایت روی GitHub Pages «استاتیک» است — یعنی فقط فایل تحویل می‌دهد و هیچ حافظه‌ای ندارد.

اول اطلاعات را در **حافظهٔ مرورگر** ذخیره می‌کردیم. مشکلش این بود:

```
گوشی مشتری                    گوشی صاحب تالار
─────────────                 ─────────────────
فرم را پر می‌کند                پنل را باز می‌کند
      ↓                              ↓
حافظهٔ مرورگر خودش              حافظهٔ مرورگر خودش
      ↓                              ↓
   اینجا می‌ماند       ✗          هیچی نمی‌بیند
```

هر مرورگر حافظهٔ خودش را داشت. **استعلام هرگز به صاحب تالار نمی‌رسید.**

Supabase یک **انبار مشترک** بیرون از مرورگرهاست:

```
گوشی مشتری ──┐
              ├──→ Supabase ──→ گوشی صاحب تالار
هر مرورگری ──┘     (انبار مشترک)
```

حالا هرکسی فرم را پر کند، اطلاعات به یک جای مرکزی می‌رود و صاحب تالار از هر دستگاهی می‌بیندش.

## ۴. امنیت — مهم‌ترین بخش

اینجا یک چیز عجیب هست که باید بفهمید: **کلید Supabase در کد سایت است و همه می‌توانند ببینندش.**

این اشکال نیست. عمدی است.

فکر کنید به **آدرس یک ساختمان**. آدرس عمومی است، هرکسی می‌داند کجاست. ولی آدرس داشتن یعنی می‌توانید بروید جلوی در — نه اینکه بتوانید وارد شوید.

کلید `anon` همان آدرس است. اینکه چه کاری **می‌شود** کرد را قانون‌های دیگری تعیین می‌کنند به اسم **RLS**:

| | بازدیدکنندهٔ معمولی | مدیر واردشده |
|---|---|---|
| ثبت استعلام | ✅ | ✅ |
| خواندن استعلام‌ها | ❌ | ✅ |
| دیدن رزروها | ❌ | ✅ |

یعنی بازدیدکننده می‌تواند نامه در صندوق بیندازد، ولی نمی‌تواند صندوق را باز کند و نامه‌های بقیه را بخواند.

⚠️ **یک کلید دیگر هم هست به اسم `service_role`.** آن یکی همهٔ قانون‌ها را دور می‌زند. هرگز جایی نگذاریدش که منتشر شود.

### رمز مدیر

رمز پنل به Supabase می‌رود، آنجا بررسی می‌شود و یک بلیت موقت برمی‌گردد. رمز هیچ‌وقت داخل کد سایت نیست.

---

## ۵. کلیدها در دو جا هستند

این نکته اول گیج‌کننده است:

| کجا | برای چه | فایل |
|---|---|---|
| روی کامپیوتر شما | وقتی محلی تست می‌کنید | `.env.local` |
| روی گیت‌هاب | وقتی سایت را منتشر می‌کند | Settings → Secrets |

**هر دو لازم‌اند.** فایل `.env.local` عمداً روی گیت‌هاب نمی‌رود (در `.gitignore` است)، پس گیت‌هاب کلیدها را از Secrets خودش برمی‌دارد.

اگر Secrets را نسازید، سایت منتشر می‌شود ولی به دیتابیس وصل نیست.

## ۶. کل مسیر، یکجا

```
   مشتری فرم را پر می‌کند
            ↓
   سایت (GitHub Pages)
            ↓
   Supabase ← اینجا RLS چک می‌کند: «فقط ثبت، نه خواندن»
            ↓
   جدول leads
            ↓
   صاحب تالار وارد پنل می‌شود ← Supabase رمز را چک می‌کند
            ↓
   پنل استعلام‌ها را می‌خواند و نشان می‌دهد
```

## ۷. کارهای روزمره

**تغییر در سایت دادید:**
```
git add -A
git commit -m "توضیح کوتاه"
git push
```
دو دقیقه بعد سایت به‌روز است.

**می‌خواهید محلی تست کنید:**
```
npm run dev
```
بعد `http://localhost:5173` را باز کنید. برای خاموش کردن `Ctrl+C`.

**فایل `.env.local` را عوض کردید:** حتماً سرور را restart کنید. این تنها فایلی است که با ذخیره‌کردن به‌تنهایی اثر نمی‌گذارد.

---

## ۸. دو اشتباهی که وقت گرفت — تا دوباره تکرار نشود

**«Actions» دو جای متفاوت است.** تب Actions در نوار بالای مخزن جایی است که اجراها را می‌بینید. اما Settings ← Actions تنظیمات مجوز است و ربطی به انتشار ندارد.

**RLS به‌تنهایی کافی نیست.** دیتابیس دو لایه چک می‌کند: اول اینکه این نقش اصلاً حق دست‌زدن به جدول را دارد (`GRANT`)، بعد اینکه کدام سطرها (`RLS`). ما اول فقط لایهٔ دوم را نوشتیم و همه‌چیز رد می‌شد.
